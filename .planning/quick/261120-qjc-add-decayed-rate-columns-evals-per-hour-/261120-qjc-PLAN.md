<objective>
Add two exponentially decayed per-worker rate columns to `worker_heartbeats`, `evals_per_hour_1h` (tau = 1 h, current speed while online) and `evals_per_hour_24h` (tau = 24 h, average contribution including downtime). They are maintained server-side inside the existing `upsert_worker_heartbeat` INSERT ... ON CONFLICT DO UPDATE, so concurrent submits stay atomic. Workers need no changes.

Purpose: a rough per-worker contribution and speed number for a fleet whose workers go online and offline at any time.
Output: model columns plus docstring, one autogenerated Alembic migration, the SQL estimator in the repository, and new tests in `tests/test_worker_heartbeats.py`.

Locked design (owner, do not revisit). Cited as L-NN in task actions:
- L-01: estimator in SQL in the ON CONFLICT SET clause: `rate_new = rate_old * exp(-dt/tau) + n_evals/tau`. dt = now() minus the EXISTING row's last_seen, in hours. Units are evals per hour.
- L-02: first insert: rate = n_evals / tau_hours for each column.
- L-03: clamp dt with greatest(dt, 0).
- L-04: two columns `evals_per_hour_1h` / `evals_per_hour_24h`, double precision, NOT NULL, server_default 0. Existing rows start at 0, no backfill.
- L-05: tau values are named module constants.
- L-06: document the read-time decay expression in the model docstring and column comments. At planning time, `grep -rln worker_heartbeats docs/ README.md CLAUDE.md` returned nothing, so per the owner's fallback the model docstring is the doc home.
- L-07: keep the heartbeat as passive telemetry inside the SAVEPOINT that swallows errors.
- L-08: record these caveats in the docstring without solving them: the unit is evals (four lanes mixed, not CPU work); the flaw-blob discarded-work path skips the heartbeat; worker_id is advisory, so machines sharing an id are summed.
- L-09: tests: first insert = n/tau; decay then add after a deterministic dt (UPDATE last_seen backwards, no sleeping, compare with tolerance); the 1h column decays faster than the 24h column; existing counters accumulate unchanged.
- L-10: migration via `uv run alembic revision --autogenerate`; ty zero errors; ruff format + check. Work happens on `main` with atomic commits. No frontend changes and no CHANGELOG entry (operator telemetry, not user-facing).

Planning-time discoveries. These are additive numeric guards, not design changes. They were verified on the dev DB (PostgreSQL 18.6) with read-only SELECTs:
- P-01: `SELECT exp(-1000::float8)` raises `value out of range: underflow`, and `exp(-700::float8)` is fine, so the threshold is about 745. A tau = 1 h worker offline for about 31 days would make the L-01 statement raise. The SAVEPOINT swallows the error (L-07), so last_seen never advances again and every later submit hits the same error: the row freezes for good, all counters stop, and Sentry gets one event per submit. The owner's literal read-time expression `evals_per_hour_1h * exp(-extract(epoch from now() - last_seen) / 3600.0)` also errors for a 40-day-idle row (the numeric exp result underflows on its implicit cast to float8). The fix is to cap the decay exponent at a named `MAX_DECAY_EXPONENT = 50.0` on the write path and in the documented read expression. exp(-50) is about 1.9e-22, which is zero for any rate. With the cap, `5.0::float8 * exp(-least(<40 days in hours>, 50))` returns 9.6e-22 without error.
- P-02: `SELECT 1e-300::float8 * 1e-30::float8` also raises `value out of range: underflow`. `n_evals = 0` is reachable on all four lanes: no submit schema in `app/schemas/eval_remote.py` sets min_length on `evals`, and entry-submit explicitly handles zero-target leases. So a run of zero-eval submits could decay a stored rate down into float8 multiply underflow, giving the same permanent freeze as P-01. The fix is a named `_RATE_ZERO_FLOOR = 1e-6` (evals/hour): a decayed term below it snaps to 0. Stored rates are then 0, or at least min(floor, 1/24), so `rate * exp(-50)` is never below about 2e-28 and cannot underflow.
</objective>
