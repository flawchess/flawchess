# Quick Task 261120-qjc: Decayed per-worker eval rate columns

Two exponentially decayed per-worker rates (`evals_per_hour_1h`, tau 1 h; `evals_per_hour_24h`, tau 24 h) are now maintained atomically inside `upsert_worker_heartbeat`'s single INSERT ... ON CONFLICT DO UPDATE, with underflow guards. No worker or call-site changes.

## What was built

- Model: two `Double NOT NULL server_default 0` columns; the class docstring documents the estimator, tau semantics, the two capped read-time expressions and the L-08 caveats.
- Migration `80050899e337` (autogenerated, docstring added): add_column x2 / drop_column x2. `alembic check` reports no drift; downgrade -1 then upgrade head verified on dev.
- Repository: `RATE_TAU_1H_HOURS`, `RATE_TAU_24H_HOURS`, `MAX_DECAY_EXPONENT`, `_RATE_ZERO_FLOOR` constants and a `_decayed_rate` SQL builder using the pre-update `last_seen`, `greatest(dt, 0)`, the capped exponent, and the zero floor. The SAVEPOINT/Sentry-swallow block is unchanged.
- Tests (5 new, 9 total in `tests/test_worker_heartbeats.py`): first insert, decay-then-add (+ 1h decays faster than 24h + unchanged counters), read-time docstring expressions run verbatim (including a 60-day idle row), 60-day offline gap, 20-step zero-eval run.

## Mutation proofs (temporary, reverted, `git diff app/` clean afterwards)

- (a) `MAX_DECAY_EXPONENT = 1e9`: long-gap test FAILED with `assert 1 == 2` (submit_count stuck at 1, the second heartbeat was swallowed by the SAVEPOINT).
- (b) `_RATE_ZERO_FLOOR = 0.0`: zero-eval test FAILED with `assert 16 == (20 + 1)` (the row froze after 16 submits, matching the predicted k of about 16).
