<objective>
Add `--lanes N` to `scripts/remote_eval_worker.py`. With it, N concurrent lease -> evaluate -> submit cycles run inside one worker process on the single EnginePool, so a many-engine machine keeps its engines busy while other lanes wait on HTTP. Measured on prod 2026-11-19: amalie-nb at `--workers 28` spends about 3 s searching and about 4 s in HTTP per tier-4 game, and its engines idle during the HTTP part. Running several worker processes per machine was rejected by the owner.

Purpose: more throughput per box with no server change. The three fleet workers that will not be updated keep their exact current behavior, because the default is 1.

Output: the flag and its lane runner in the worker script, tests that each fail when the feature is reverted, and an operator note in REMOTE_WORKER.md.

## Design decisions (planner discretion; the executor implements these exactly)

- K-01 (single-loop path): `run_worker` branches on `lanes`. At 1 it awaits `_run_loop` exactly as today, with `lane=None`. Lanes above 1 go through the new `_run_lanes`. The EnginePool and the httpx clients are built once in `run_worker` either way. One `httpx.AsyncClient` per target is shared by all lanes, and httpx clients are safe for concurrent requests.
- K-02 (lane runner): `_run_lanes` starts one task per lane in an `asyncio.TaskGroup`. Tasks are named `_LANE_TASK_PREFIX + index`, and each awaits `_run_loop(..., loop=True, lane=_LaneContext(...))`. No lane state lives in module globals. Each lane gets a frozen `_LaneContext(index, entry_lock, streak)`; the lock and the streak are shared by all lanes.
- K-03 (worker-id safety, verified in app/routers/eval_remote.py and app/services/eval_queue_service.py). Same X-Worker-Id for every lane, with one asyncio.Lock on the entry rung only. Per rung:
  - Rung 1, explicit atomic (tier-1/2): safe. `_claim_queued_job` claims one eval_jobs row per call with SKIP LOCKED and stamps `leased_by`. Completion is keyed on the echoed `job_id`. Nothing looks jobs up by `leased_by`.
  - Rung 2, entry-ply: UNSAFE. `/entry-submit` selects every game with `entry_eval_leased_by == worker_id` and an unexpired lease, then stamps all of them `evals_completed_at`. Lane A's submit would therefore close lane B's in-flight batch without evals, and lane B's later submit would find nothing leased and drop its evals. Mitigation: hold one per-process `asyncio.Lock` from `/entry-lease` through `/entry-submit`. A lane that reaches rung 2 while another lane holds an entry lease WAITS for the lock instead of skipping to rung 3, which keeps the ladder order unchanged. The cost: during a big import (the entry rung only answers 200 when the backlog is 300 or more), entry work runs one lane at a time, which is today's throughput and no regression. Distinct per-lane worker ids were rejected: they would multiply the `worker_heartbeats` registry rows per machine and break the brief's same-X-Worker-Id requirement.
  - Rung 3, idle atomic (tier-3): no lease and no worker id (`_claim_tier3_derived` is a plain lottery). Two lanes can draw the same game, exactly as two separate workers can today. Accepted, no change.
  - Rung 4, flaw-blob (tier-4): safe. `blob_claim_lease.try_lease` refuses any unexpired lease whatever the owner, so one owner cannot hold the same game twice. `release_lease(game_id, owner)` frees only that game, so two lanes with one owner holding different games never interfere.
  - Rung 5, bestmove (tier-4b): no lease and no worker id. Same as rung 3, accepted.
  - The `worker_heartbeats` upsert: the lanes now share one row, which becomes a short row-lock wait. The upsert runs last in each submit transaction, inside its own SAVEPOINT, and failures are swallowed. Accepted.
- K-04 (watchdog): `_Heartbeat` keeps one progress slot per lane. `last_progress` becomes a read-only property returning the minimum over the slots. `mark(lane=0)` updates that lane's slot and rewrites the file only when the marking lane held the oldest slot before the mark. `_watchdog_checker` and `_is_stalled` are unchanged and simply read the minimum, so a healthy lane can never refresh a wedged lane's progress. At lanes=1 every mark is by the oldest lane, so the file is written on every mark, as today.
- K-05 (exception isolation): this comes from the existing per-cycle boundary in `_run_loop` (loop=True never lets an `Exception` escape). Only cancellation, or a BaseException escaping a lane, ends a lane. A BaseException other than cancellation makes the TaskGroup cancel the siblings and raise. `run_worker`'s finally then stops the pool, the child exits non-zero and the supervisor relaunches it: fail-whole-process for a case that should not happen.
- K-06 (idle and Sentry volume): per-lane idle sleep = `idle_sleep * lanes`, and lane i's first cycle starts after `i * idle_sleep`. Fully-idle polling and the "Queue fully empty" log line therefore stay at about one ladder per `idle_sleep` in aggregate, as today, and pickup latency for new work stays about `idle_sleep`. The failure back-off is scaled the same way. One `_TransientStreak` is shared by all lanes, so a sustained outage escalates one warning, not N. A success in any lane resets the streak, matching today's "any successful cycle resets" rule.
- K-07 (cap and the stall threshold): hard cap `lanes <= ceil(workers / MIN_ENGINES_PER_LANE)` with `MIN_ENGINES_PER_LANE = 2`, enforced by `parser.error` (rejected, not silently clamped, because the cap is what keeps the watchdog argument sound). The argument:
  - `EnginePool._acquire_and_analyse` takes an engine from its queue BEFORE `asyncio.wait_for` starts the per-search timeout. Queueing behind other lanes therefore never creates eval holes; it only stretches a lane's wall clock.
  - With L lanes on W engines, a lane's pass waits behind at most the other L-1 lanes' in-flight passes.
  - In the all-timeout worst case (the existing comment's model: one 100-position pass at 5 s plus the 8 x 15 s retry pass), the cycle bound is ((2L-1) x 500 s + 120 s) / W.
  - That bound stays at or below the 620 s single-lane `--workers 1` case exactly when L <= ceil(W/2).
  - So STALL_THRESHOLD_S (720 s) and the server's BLOB_LEASE_TTL_S (720 s, derived from it in app/services/blob_claim_lease.py, whose comment stays true) need no change.
  - The sizing hint is softer: `RECOMMENDED_ENGINES_PER_LANE = 4` (about 7 lanes at `--workers 28`).
- K-08 (modes and shutdown): `--once` and `--dry-run` force a single lane via `_effective_lanes`. `--once` is one game by definition. A looping `--dry-run` leases without submitting, so N lanes would strand N leases per cycle. A one-line note is logged when a requested `--lanes > 1` is overridden.
  - SIGINT behaves as it does today. Python 3.14's `asyncio.Runner` turns the first SIGINT into a cancel of the main task, so today's single loop does NOT finish its in-flight submit; the cycle is cancelled and the server lease TTLs recover the work. With lanes, that cancel reaches `_run_lanes`, the TaskGroup cancels and awaits every lane, and `run_worker`'s finally stops the pool once.
  - The brief's wording ("each lane finishes its in-flight submit as the single loop does today") does not match the current code. A graceful submit-drain would change lanes=1 behavior too, so it is not added; this is flagged to the orchestrator.
