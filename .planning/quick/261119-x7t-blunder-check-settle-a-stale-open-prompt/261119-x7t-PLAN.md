<objective>
Fix the stale-prompt resume in blunder check. When a resume (`start_window`) finds an open prompt more than `ANSWER_CEILING_S` past its `prompted_at`, the server settles it as a timeout with the normal timeout grading and reopens the sequence on a Ready gate before the next move. Ready (`begin_window`) then issues the NEXT move's prompt with a full clock. Reloads within the ceiling behave exactly as today. A stale timeout that ends the window returns an ended state that the client routes to the window's solution.

Purpose: prod incident (user 28, 2026-11-19). The user abandoned sequence 1 at move 3 (prompted 18:27:39 UTC) and pressed Start two hours later. `start_window` returned the open prompt with 0 ms left and no gate. The client auto-submitted a timeout (client_elapsed_ms 0, server_elapsed_ms 7,410,542) and move 4's clock started at once, before the user had looked at the board.

Output: backend settle-on-resume plus a gate at any move index (no migration), a new `outcome` field on the window-start payload, client support for a mid-sequence gate and an ended resume, backend and frontend tests, and a CHANGELOG bullet.

Locked owner decisions (cited as L-NN in the tasks; do not re-litigate):
- L-01: a resume (`start_window`) that finds an open prompt past `ANSWER_CEILING_S` (17 s) after `prompted_at` settles it as a timeout with the normal timeout grading: a good move costs `SAFE_TIMEOUT_PENALTY_POINTS` (1) from the pot (never below 0), and a timed-out blunder ply is a miss.
- L-02: after a settle that does not end the window, the sequence reopens on a Ready gate. The next prompt gets no `prompted_at` until Ready. `begin_window` then issues the NEXT move's prompt with a full clock, not move 1.
- L-03: reloads within the ceiling are unchanged. The original `prompted_at` stands and a reload never buys time (D-18).
- L-04: if the stale timeout ends the window (the blunder ply timed out, or it was the last judged move), the resume returns an ended state, not a gate.
- L-05: accepted trade-off: a user can deliberately abandon a prompt to study the position, at the price of that timeout. No further countermeasure.
- L-06: the settle writes rows, so the resume path takes the same window row lock the answer path uses (`for_update=True`) and stays idempotent under a double resume.
- L-07: no DB migration.

Planner discretion (decided here):
- Representation of "gate before move N": a started window with no outcome and no open prompt row. The gate's move is the last answered `move_index` + 1, or move 1 when nothing is answered. This state could not exist before (an answer that continues the window always inserts the next row in the same transaction), so no flag or column is needed. `awaiting_ready` becomes "no open prompt row" instead of "no rows at all".
- A server-settled row stores `answer = TIMEOUT`, `client_elapsed_ms = NULL` (the column is already nullable: the client never answered, which tells these rows apart from client timeouts in the data) and `server_elapsed_ms` = the real elapsed time.
- Ended resume: `start_window` returns the normal `WindowStartResponse` with a new `outcome` field set (`missed` or `cleared`). The client maps it onto its existing `solution_loading -> solution` flow, the screens an in-session ending answer reaches after its feedback, so the user sees why the sequence ended. The better-move resume (a caught window) also reports `outcome = "caught"`, so the field is truthful whenever the payload describes an ended window. Rejected alternatives: (a) a 409 `window_ended` would be rolled back by the router's `_guarded` (the settle would vanish), and the client shows "Failed to start the sequence"; (b) settling inside `POST /sessions` so `current_position` skips the window would hide the outcome from the user, and `start_window` would still need an answer for a direct reload.
- `begin_window` does not settle anything: `start_window` is the only resume path. A begin that finds an open row keeps today's idempotent behaviour (the original stamp, the real time left). A begin that answered with a gate would also trip the client's `windowBegun` loop guard.
- Gate copy stays as it is ("Check out the position, you play {side}. ..."). Its turn sentence now reads the gate's board, so a mid-sequence gate says "It's your turn." The first-sequence rules intro condition (position 0 and `first_session_done === false`) is unchanged. On resume there is no feedback flash for the settled timeout: the pot in the progress row already shows the server's points.
- The settle reuses the answer path's grading through one extracted helper (`_grade_row`), and the ceiling comparison gets one named predicate (`is_past_ceiling`) that `effective_answer` also uses, so the stale check can never drift from the answer ceiling.
</objective>
