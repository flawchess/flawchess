<objective>
Ending an impersonation session from the pill's x currently calls logout, so the superuser is signed out and has to log in again. Make the x return the admin to their own session on /admin, purely in the frontend, by stashing the admin's JWT in localStorage when impersonation starts and restoring it when it ends.

Locked design (user-approved, implement exactly; cited as LD-n in tasks):
- LD-1: impersonate() copies the current admin auth_token into the localStorage key admin_return_token (named constant) before overwriting auth_token, and only when no stash exists (defensive against a nested or repeat call clobbering the stash with an impersonation token; the backend already forbids nested impersonation).
- LD-2: endImpersonation() on AuthState: stash present means move it back into auth_token, remove the stash, queryClient.clear(), hard-navigate to /admin (hard nav is load-bearing: resets the query cache and the Umami in-memory identity, Phase 229 D-07). No stash means fall back to logout().
- LD-3: ImpersonationPill x calls endImpersonation() instead of logout; doc comment updated; aria-label stays "End impersonation session".
- LD-4: Regular Logout stays a full logout and also removes the stash. login, loginWithToken, loginAsGuest, register (if it sets a token) and logoutForPromotion also clear it, so a stale admin token can never resurface.
- LD-5: An expired stashed admin token needs no special handling; the existing 401 flow sends the user to /login.
- LD-6: No backend endpoint that mints an admin token from impersonation claims (a leaked 1h impersonation token could be traded for a 7-day admin token, defeating Phase 62 D-03). Say so in the fix-site comment.
- LD-7: Use the real /admin route path. App.tsx declares it only as a string literal (Route path, ADMIN_NAV_ITEM, title map), with no exported constant, so useAuth.ts gets its own named constant.
- LD-8: Vitest coverage for useAuth and ImpersonationPill.

Planner discretion (documented choices):
- PD-1: The stash is written after the impersonate POST succeeds, immediately before auth_token is overwritten, and the current token is read from localStorage. Do not read the `token` state there: impersonate is a useCallback with empty deps, so that value is stale.
- PD-2: The storage-key constant is exported from frontend/src/lib/impersonation.ts so useAuth.ts and api/client.ts can share it. Defining it in useAuth.ts would need client.ts to import useAuth.ts, which already imports client.ts (an import cycle).
- PD-3: The 401 interceptor in api/client.ts also removes the stash next to auth_token. This extends LD-4's "never resurface" rule to the session-expiry path: when the 1h impersonation token expires, a 7-day admin JWT must not stay behind in storage with no visible session. The UX matches today's (the admin signs in again either way).
- PD-4: refreshAuthToken leaves the stash alone. It is a same-user token refresh, and clearing the stash there would strand an impersonating admin.
- PD-5: register delegates to login, and loginAsGuest, the OAuth callback page and RegisterForm all delegate to loginWithToken. So the removal lives only in login and loginWithToken (plus the logout paths). register and loginAsGuest get no duplicate removals.
- PD-6: data-testid btn-impersonation-pill-logout stays unchanged. It is a stable automation hook referenced by the Phase 62 verification.

Out of scope (do NOT change; already flagged to the orchestrator): when a guest account is impersonated, App.tsx's GUEST-05 effect calls /auth/guest/refresh with the impersonation token and refreshAuthToken swaps in a real 30-day guest token. That is a pre-existing issue. Do not touch App.tsx or any backend file.

Purpose: superusers can hop between impersonated users and the admin page without re-entering credentials.
Output: stash/restore logic in useAuth, the pill wired to it, stash hygiene on every session start/end path, tests, a CHANGELOG bullet.
</objective>
