# Per-user herring serve order with phase interleaving

## Problem (prod, 2026-11-03)

`herring_stmt` orders globally: `(qualifying >= 3) DESC, source_played_at DESC NULLS LAST, id ASC`.
Every user is served the identical herring sequence:

- herring_pool row 5344 served to 479 of 485 users; only 232 of 3,527 servable rows ever served
- generator builds phase-balanced thirds, but serving ignores phase: 1,808 opening solves vs 754 middlegame
- herring guess-accuracy stats are dominated by ~a dozen positions

## Task 1: per-user hash order + phase rotation in `herring_stmt`

Files: `app/services/train_pool.py`

New ORDER BY (TOTAL, stable per user, differs across users):

1. `preferred DESC` (qualifying_count >= HERRING_PREFERRED_QUALIFYING_MOVES), unchanged preference
2. `row_number() OVER (PARTITION BY preferred, phase ORDER BY user_hash, id)` ASC: round-robin across phases
3. `user_hash` ASC: within a round, the phase order is per-user pseudo-random. A fixed `phase ASC`
   tiebreak would starve endgame (2 herring slots per 8-puzzle session, exclusion recomputes ranks
   after every session, so opening + middlegame would win every round)
4. `id` ASC: final tiebreak

`user_hash = md5(user_id || ':' || herring_pool.id)`. The window runs after WHERE, so ranks are over
the not-yet-served rows. Docstring: rewrite the ordering section; correct the claim that
`WINNABILITY_FLOOR_ES` is enforced at generation time (the generator only applies the stored-eval
`HERRING_PREFILTER_ABS_CP` prefilter). `ix_herring_pool_recency` is no longer used by any query;
leave it (no migration), note it on the model.
