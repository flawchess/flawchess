## Data-source decision (spec asked: pick a response, prefer SolveResponse, justify)

**Decision: read the values from the game card the footer already fetches. No backend
change, no new field on SolveResponse or PuzzleRevealResponse, no edit to `frontend/src/types/train.ts`.**

`TrainRevealGameFooter` already calls `useLibraryGame(puzzle.game_id)`, which returns
`GameFlawCard` (`app/schemas/library.py`). That card's `eval_series: list[EvalPoint]` already
carries, for every ply, exactly the two values this line needs:

- `EvalPoint.clock_seconds`: the mover's remaining clock AFTER the move at that ply.
- `EvalPoint.move_seconds`: increment-corrected time spent on that move (1 dp).

Both are computed once in `app/services/library_service.py` `_build_eval_series` (around
lines 216-255: same-side prior clock, `_resolve_increment(game)`, first move of each side
seeded with the base time) and both are forced to None for daily/correspondence games via
`is_correspondence_time_control`. The puzzle's `ply` is the flaw ply: `GamePosition` at
`solve.ply` is the row whose `move_san` is the played (flawed) move (see
`reveal_for_puzzle` in `app/repositories/train_repository.py`), and its `clock_seconds` is the
clock after that move (same convention as `PositionAt` in `library_repository.query_flaws`).
So `eval_series.find(point => point.ply === puzzle.ply)` is the flawed move.

Why this beats SolveResponse:
- Zero duplication: the spec's "reuse existing computation, no duplicated formula" is met
  literally (same server values, no new call site of the formula, no new SQL).
- SOLV-05 is untouched: the card query is the existing post-solve-gated one (the footer only
  mounts once `verdict` exists), so nothing new can leak pre-solve.
- No layout shift: the clock line and the "Game:" line come from one query and appear in the
  same render. A SolveResponse field would paint the clock line before the game line loads.
- No stale-bundle work: `trainRevealCache` restores old `verdict` objects without new keys
  (the reason SolveResponse fields are optional in `types/train.ts`); the card is refetched.
- The reveal's Analyze button opens the same game, whose eval-chart tooltip shows these
  same numbers, so the two surfaces agree by construction.
- SR puzzles come from `game_flaws`, which only exist for fully evaluated games, and
  `eval_series` is populated whenever `games.full_evals_completed_at` is set. If it is ever
  null, the line is simply omitted (the spec's "neither" fallback).

Rejected: new `clock_seconds`/`move_seconds` on SolveResponse (an extra query in
`record_solve` plus another caller of the move-time formula for data the client already
holds) and on PuzzleRevealResponse (async fetch, RESEARCH Pitfall 1 window).

Known semantic difference vs the Library flaw card (`library_repository._compute_move_seconds`),
accepted: the eval series seeds each side's first move from the base time (flaw card: None for
ply < 2) and clamps a negative clock anomaly to 0.0 (flaw card: None). A Train puzzle at
ply 0-1 practically never occurs, and matching the analysis board is the better consistency target.

Backend tests for the data contract already exist and run as a regression check (Task 3):
`tests/services/test_eval_chart_service.py` covers the value, increment, first-move base
time, negative clamp, no-%clk None, and daily (`1/86400`) / correspondence (`1/259200`) None.

## Format decisions (Claude's discretion, spec allowed)

- Think time: `Math.round` to whole seconds first, then split. Below 60: `13s` (0.3 gives
  `0s`). From 60 on: `1m 20s`; an exact minute drops the zero part: `2m`. No hours (a single
  think over an hour is vanishingly rare; `75m 3s` still reads fine). Rounding before the
  split means 59.6 gives `1m`, never `60s`.
- Clock: floor to whole seconds (matches `formatClock` in `frontend/src/components/library/FlawCard.tsx`),
  `m:ss` below one hour (`3:56`, `0:05`, `0:00`), `h:mm:ss` from one hour on (`1:25:30`, `1:00:00`).
- Copy has no em-dashes: commas and a final period only.
