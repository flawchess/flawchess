## Planning notes

- **Discretion adopted:** `feedbackAskDays(profile)` as the one shared predicate all three surfaces
  read (returns `profile.active_days` when the ask is active, else null), and no "shown" Umami event
  (views are DB-known; frontend/CLAUDE.md forbids trackFeature on mount). The app-level FeedbackModal
  host (RESEARCH Pitfall 1) is plan 03.
- **Umami click events kept (checker info item, decided per frontend/CLAUDE.md):** the rule is "track
  only what the browser knows and the database cannot", and it explicitly gives an event to state rows
  overwritten in place. Two facts are browser-only here. (1) Which surface got the click:
  `users.prompt_state` stores no surface, while `trackFeature` stamps the route's page, which is
  'library' for the Import page (/library/import), 'train' for the Train landing and 'bots' for the
  roster, so the event answers which surface earns the feedback. (2) Click history:
  `prompt_state.feedback_v1` is overwritten in place, a round-2 view replaces the object with
  `{round 2, views 1, last_view_date}` and drops round 1's `status`/`snoozed_by`/`snoozed_at_days`,
  so a round-1 "Maybe later" click is no longer in the DB once round 2 starts. Neither event carries
  the day count, the round or any free value (D-04 enumerated literals only).
- **Plan split (revision):** the app-level modal host, the ask placeholder and the modal open store
  moved to plan 03 so this plan stays inside the per-plan budget. Until plan 03 lands, "Sure!" records
  done and hides Hilda without opening the modal; the phase merges as a whole, so this intermediate
  state never ships.
- **View responses never patch the cache.** A scoped mutation runs `onMutate` immediately even while
  it waits behind an in-flight view, so a view response that patched `active: true` would resurrect a
  bubble the user just dismissed. Only snooze/done patch the cache. A profile poll that lands inside
  the ~50 ms snooze round trip can still flash the bubble once (accepted, low).
