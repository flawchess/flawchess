## Planning notes

- **Separate version constant (RESEARCH Pitfall 4):** `TELEMETRY_SCHEMA_VERSION` is shared by both
  patches; bumping it would make every solve POST send `v: 2`, which `SolveTelemetry` rejects and the
  `SolveRequest` wrap validator then silently drops. So a new `REVIEW_TELEMETRY_SCHEMA_VERSION = 2`.
- **Stored `v` semantics:** solve and review patches both write the top-level `v` and the merge is last
  write wins, so a row's `v` reflects the LAST patch: after a v2 review flush the stored row says `v: 2`
  while its solve keys are v1-shaped. Analysis branches on `v` for review keys only. Document this in the
  docstring.
- **Exact v2 key names (Claude's discretion, research recommendation):** `review_chips_selected`
  (distinct chips selected beyond the default You chip), `review_chips_total` (chips shown),
  `review_strip_expanded` (phone only). Both counts reuse `TelemetryCardCount` (cap 10).
- **Parity test:** NOT touched here. Plan 09 adds the `REVIEW_TELEMETRY_SCHEMA_VERSION` row together with
  the TS constant (adding the TS constant now would be an unused export that knip rejects).
- Spec-less probe fallback skipped this run: the phase has no requirement IDs to probe.
- No migration (the column is JSONB); no `bin/reset_db.sh`.
