## Planning notes

- **Trigger needs the runner-up (D-19):** measured headless this phase, at 1.5 s the sharp `su`
  (d1d5) reads ABOVE the key (Qh4) on the user-28 FEN, so without the exclusion every played `su`
  would burn a pointless 6 s re-check that the server then overrides (D-02).
- **Node cap (RESEARCH Pitfall 1):** the 2M grading cap bound at 2.7 s in Node 24 on the user-28 FEN,
  so a "3 s" re-check under that cap is not deeper. The re-check cap scales with the movetime and
  doubles for headroom (8,000,000).
- **Re-check failure (D-20):** `recheckMove` never rejects; timeout, engine error, a superseded
  puzzle or a missing anchor all resolve null and the 1.5 s grade is posted without a payload.
- **No Umami event:** the re-check is not user-initiated and every one is recorded in
  drill_solves.recheck (frontend/CLAUDE.md: skip what the database already says).
- **Display caveat (RESEARCH Pitfall 4):** D-16 unclamping follows the phone's confirmed outcome; in
  the rare case the server refuses the claim because the live puzzle type changed, the evals stay
  unclamped while the guess copy is the standard one. Accepted.
- **Split with plan 05 (checker scope_sanity, executor context budget):** this plan owns the engine,
  the trigger, the POST record and the failure fallback; plan 05 owns everything the user reads (the
  `isRechecking` state and "Taking a closer look…" D-12, the D-15 guess line), the CHANGELOG and the
  phase-wide gate. The `isRechecking` state is created in plan 05 together with its only consumer,
  because an unread state variable fails `noUnusedLocals` and eslint here. Between the two plans the
  bubble keeps "Checking your move…" for the whole grade-plus-re-check wait; both plans ship together.
- **D-05 gate (checker key_links info):** the old dotted-access grep missed destructured or bracket
  reads, so this plan uses two gates: (A) every production file naming the three snake_case
  TrainPuzzle fields on a non-comment line is one of TrainReveal.tsx (post-attempt), TrainSolveScreen.tsx
  and types/train.ts; (B) inside TrainSolveScreen.tsx every such line is a dotted `puzzle.` access or
  the post-attempt `verdict?.puzzle_type`. New code in trainRecheck.ts and the hook takes the values
  as camelCase parameters.
