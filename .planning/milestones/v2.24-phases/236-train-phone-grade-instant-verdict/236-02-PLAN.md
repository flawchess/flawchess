<objective>
Client half of Part 1 of SEED-193: the phone already holds its tier and the 1.5 s key/played
expected-score pair before the POST; this plan surfaces the two depths with them as a
`phoneReading` on `GradeResult` and sends it as the `phone_grade` record on every keyed solve that
takes today's path (D-13: phone-graded moves and played == key). It also lands the client types for
the server-graded set and the D-11 rule that a server-graded move is never re-checked.

Purpose: plan 01 stores the record; plan 05 builds the instant path on the same `phoneReading` and
the same `serverGradedMoves` read site. Runs in parallel with plan 01 (no shared files; the wire
shape below matches plan 01's `PhoneGrade` exactly).

Output: `lib/trainPhoneGrade.ts`, new TS wire types, `GradeResult.phoneReading`, the POST field, the
`shouldRecheck` exclusion, tests.
