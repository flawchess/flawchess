<objective>
Make the session streak require every mode that is switched on (D-02), end to end, on top of plan 01's schema and dated
blunder-check sessions.

Purpose: the streak machine is the load-bearing piece of Phase 251 and D-18 ships it to every streak holder at once with no
prod rehearsal. This plan keeps the pure tick machine byte-for-byte and changes only what feeds it: a set of complete days
computed from both session tables and the current per-mode sizes, plus one idempotent eager entry point that every
completion event calls (a puzzle session's last solve and a blunder-check finish).

Output: the `day_is_complete` rule, the complete-day feed into `tick_days`, `apply_day_completion`, blunder-check sessions
sized from the settings row and crediting the day on finish, pool eligibility for blunder-check-only users, the launch-day
test matrix from CONTEXT Specifics, and every pre-existing test that pinned the puzzle-only rule restated with an explicit
blunder-check size of 0.
</objective>

## Planning notes (recorded choices)

- Split from the original plan 01 during plan revision (2026-11-18) so each plan stays under the per-plan file budget once
  every affected pre-existing test file is listed. Plan 01 lands the schema and the dated blunder-check sessions; this plan
  lands the rule. The interface names below are unchanged from the original plan, only their owner moved.
- `train_settings.streak_credited_on DATE` (column added by plan 01) is the idempotency key of the eager path. RESEARCH
  proposed a `was_complete_before` guard computed with the current sizes; that misses the sequence "puzzles done with BC at
  0 -> day credited -> BC raised -> BC done", which would mint a second freeze. A stored "last credited day" closes it. Plan
  01 backfilled it to `streak_settled_through` so a user who completed today's puzzles before the deploy is not credited
  twice.
- `train_settings.blunder_check_streak_from DATE` (column added and backfilled by plan 01): days before it are judged with
  blunder check not required, so pre-launch days stay as judged and the "N of M this week" caption does not drop for every
  streak holder on launch day. NULL on rows created after launch (rule always applies).
- Accepted assumption A8 (RESEARCH Pitfall 4, measured on prod 2026-11-18: 23 of 635 rows, 3.6%, have a sparse mask):
  blunder-check sessions are dated `local_today` like a fresh puzzle session; a sparse-mask user who splits the two modes
  across two days can lose that day. Accepted for launch, surfaced to the owner.
- Accepted assumption A6 (deviation from the orchestrator default, reason in RESEARCH Pitfall 3): puzzles are required
  whenever their size is above 0. `pool_state` is not "nothing to serve" (sharp fillers always compose a warm-up).
