dot on it (D-10, D-11), and every account that exists at deploy starts with the launch route done (D-16, D-22) so the

requests no skip while the first unresolved step is locked, and deleting a user's games removes an existing stamp so

get the whole onboarding route.

## Assumptions recorded for the plan check

These are planner choices inside the CONTEXT "Claude's Discretion" area (locked targets: how the D-23 pause is
implemented and what happens to a step that was already current when its target locked again).

- **A-7 (D-23 re-lock: restart, not resume):** a step is never stamped `current` while its target is locked (the
  arbiter has no candidate then), so for a zero-game account the clock of a games-requiring step only starts once the
  nav unlocks. A step that was already current can lose its target again in two ways. (1) All of the user's games are
  deleted. Every such path calls `game_repository.delete_all_games_for_user` (`DELETE /api/imports/games`, the
  inactive-guest purge in `guest_cleanup_service`, the operator script `scripts/reimport_games.py`), so that function
  removes `feature_route.current` in the caller's transaction; the skip guard (`current.step = :step`) then refuses a
  skip while the account has no games, and the client stamps the step afresh on unlock, so the clock restarts and no
  locked day counts. The removal is unconditional, so a games-free current step (Train, Bots) also restarts its
  clock; that only gives the step more days, after a rare delete, and keeps games-requirement knowledge out of the
  server.
  (2) A lock shorter than an active day: `useReadiness` reports `tier1` false until its first fetch on every page
  load, and while an import job is in flight for a user who already has games. These leave the stamp in place: the
  clock counts whole active days, and removing the stamp on them would restart the clock on every page load or
  re-sync, so a games-requiring step would never auto-skip (D-10). The client still requests no skip during such a
  lock (no candidate); a skip that falls due is posted once the nav unlocks. A resume-style pause (storing a locked
  interval) was rejected: it needs extra state and writes that D-11 discourages, and restart reaches the same
  property.
- **Server skip guard and the lock:** the server does not compute the lock (game count plus import readiness). The
  client rule plus the removed stamp suffice: a zero-game account holds no `current` stamp on a games-requiring step,
  and any other early or locked-time skip would move only the caller's own route (T-255-07, T-255-17).
