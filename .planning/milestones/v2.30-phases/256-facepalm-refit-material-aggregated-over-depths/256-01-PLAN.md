<objective>
Put the material aggregate over the odd depths into both score twins, proven end to end for the
decaying mean, and move the app and service-test callers of the twins from the depth-3 scalars
to the stored arrays.

Purpose: CONTEXT D-06 needs the score to read the loss and the missed gain from depths 1, 3, 5, 7,
9 instead of depth 3 alone, in the Python twin and the SQL twin alike (254 D-01: the score stays a
query-time expression, so a later refit is a constants change). Nothing changes for users yet:
the defaults keep `material_input = "depth_3"` and `loss_gate = None`, so every shipped score is
identical until plan 08 ships the refitted constants.

Output: `app/services/facepalm_material.py` (new), the new model and facts fields, the `loses`
gate function, arrays through `maia_flaw_scoring`, the reader-test seed helper and the owner
fixtures. Plan 02 moves the calibration cache and the fit loader to the arrays. The first-stable
input arrives in plan 03 (it extends the `MaterialInput` Literal); the fit's use of the inputs
arrives in plans 04 to 06.

Intermediate state between this plan and plan 02 (one wave): this plan removes the scalar
`played_3` / `best_3` constructor parameters of `FacepalmFacts`, so the script-side callers in
`scripts/blunder_check/sample.py` and `scripts/blunder_check/fit_facepalm.py`, and with them
`tests/scripts/test_blunder_check_calibration.py` and `tests/scripts/test_fit_facepalm.py`, fail
until plan 02 moves them. Every verify in this plan is scoped to files this plan migrates; the
plan-level run excludes exactly those two test files; plan 02 ends with the full suite and
`uv run ty check app/ tests/ scripts/` green. Do not touch `scripts/` here.
</objective>
