<objective>
Turn a `flagged` audit row into a repaired game: `confirm` at the drain's own 1M-node
budget with an overwrite gated on the measured floor (CACHEFIX-04), `propagate` the new
value into every carrier `game_positions` row that still holds the old cached value
(CACHEFIX-05), and `rederive` each affected game's flaws, oracle counts and drills through
the drain's own classifier without destroying months of tier-4 blob work (CACHEFIX-06).

Purpose: this is where the user-visible damage is actually undone — the spurious
lucky-blunder / squandered-blunder pairs in the opening disappear here, not in the cache.

Output: three working stages, the `refresh_game_oracle_counts` promotion, the D-04
concurrency invariant closed on both sides, and `backfill_flaws.py --from-repair-table`.
</objective>

## Decisions recorded by this plan

- **D-04 resolved — advisory lock on both sides, not `FOR UPDATE`, not pausing the
  lotteries.** `rederive` executes `SELECT pg_advisory_xact_lock(:lock_key)` with
  `_game_write_lock_key(game_id)` as the FIRST statement of its per-game transaction. This
  is the lock `apply_full_eval` has taken since 2026-08-23 (FLAWCHESS-9F / 8G), so rederive
  serializes against both live write lanes. `SELECT … FROM games … FOR UPDATE` was rejected:
  a repo-wide grep finds zero `FOR UPDATE`/`with_for_update` against `games`, so a games-row
  lock would serialize rederive against nothing. The no-resurrect half of D-04 already holds
  by construction — both of the blob lane's `game_flaws` statements are UPDATEs, never an
  INSERT or upsert — so what task 4 adds is the *other* defect D-04's window exposes: the
  blob submit reads `null_flaw_plies` in a session that closes before its write session
  opens, and an ORM bulk-update-by-PK raises `StaleDataError` (FLAWCHESS-8D) when a ply
  vanished in between, turning a 200 into a 500 and losing the blobs. Fix: the same advisory
  lock **plus an in-lock re-read** of the surviving flaw plies; the re-read is the
  load-bearing half, the lock alone does not close the window.
- **RESEARCH open question 1 resolved — the rederive loop lives in
  `scripts/opening_cache_repair.py`**, calling `_classify_and_fill_oracle`.
  `scripts/backfill_flaws.py --from-repair-table` is a **thin delegating wrapper** onto that
  runner. This honours CACHEFIX-06's literal wording ("via
  `scripts/backfill_flaws.py --from-repair-table`") and its actual constraint ("no second
  classifier call site") at the same time. Refinement reason: `backfill_flaws.py`'s own write
  path is delete-then-insert, which would wipe `allowed_pv_lines`, `missed_pv_lines` and all
  8 tactic-tag columns for every repaired game — undoing tier-4 blob work the fleet spent
  months producing. That branch stays for its existing threshold-recompute use and gains a
  docstring warning.
- **RESEARCH open question 3 resolved — `blobs_pending=True`** for the rederive classifier
  call. `False` would re-mint the pre-Phase-143 gate-free raw tactic tag on any newly created
  flaw (the Phase 147 strict-zero violation); `True` gives it NULL and leaves it to tier-4,
  matching both live lanes.
- **CACHEFIX-06's `refresh_game_oracle_counts` is a rename, not an extraction.** Phase 214
  already extracted the block as `_write_oracle_counts` at `app/services/eval_apply.py:1311`;
  it has exactly one caller. Do not resurrect `scripts/archive/backfill_accuracy_acpl.py`.
- **Seed step 5.4 needs no new code.** `_classify_and_fill_oracle` ends with
  `_refresh_blobs_completed`, which clears `games.blobs_completed_at` bidirectionally when a
  blob-less flaw appears; the tier-4 lottery predicate consumes that. `_missing_flaw_pv_targets`
  is an in-tick helper, not the re-arm mechanism — do not call it here.
- **D-08 / D-09 honoured:** `herring_pool` rows at repaired plies are counted into
  `herrings_touched` and never deleted (a pool row is self-sufficient: it stores its own
  `fen`, `arriving_move_uci`, `mover_color` and its own MultiPV-5 `ladder`, and ~91% of served
  herrings belong to another user's game). `drill_items` with no surviving flaw are deleted;
  `drill_solves` are kept; no `drill_items` are created for flaws the repair adds.

Add the `propagate` stage, gated on `confirm_finished_at`.

For each `confirmed_bad` audit row with `repaired_at IS NULL`, in ONE transaction:

1. Run the eval rewrite as a single statement: `UPDATE game_positions p SET eval_cp =
   CAST(:new_cp AS smallint), eval_mate = CAST(:new_mate AS smallint) FROM game_positions n
   WHERE n.full_hash = CAST(:full_hash AS bigint) AND n.ply BETWEEN 1 AND 20 AND p.game_id =
   n.game_id AND p.user_id = n.user_id AND p.ply = n.ply - 1 AND p.eval_cp IS NOT DISTINCT
   FROM CAST(:old_cp AS smallint) AND p.eval_mate IS NOT DISTINCT FROM CAST(:old_mate AS
   smallint) RETURNING p.game_id, p.user_id, p.ply, n.ply AS hash_ply`. The
   `n.ply BETWEEN 1 AND 20` bound is what keeps `ix_gp_full_hash_opening` usable — it is the
   index's own partial predicate, so do not widen it. Every bind uses `CAST(x AS t)`, never
   `x::t`: asyncpg cannot infer the parameter type of a NULL bind on the
   `IS NOT DISTINCT FROM` comparison and raises `could not determine data type of parameter`.
2. Run a second statement over row `n` itself, replacing `best_move` and `pv` only where they
   are `IS NOT DISTINCT FROM` the audit row's `old_best_move` / `old_pv` — i.e. only where
   they were transplanted too. `best_move` at row P is the best move FROM row P's own
   position and is NOT shifted, and `pv` is written only at flaw-adjacent plies, so the pv
   branch will fire rarely; return the two rowcounts separately.
3. Insert one `opening_cache_repair_rows` row per RETURNING row (`game_id`, `ply`,
   `full_hash`, `old_cp`, `old_mate`, `new_cp`, `new_mate`, `best_move_replaced`,
   `pv_replaced`), batching the VALUES with `CAST()` casts. Because the PK is
   `(game_id, ply)`, use `ON CONFLICT (game_id, ply) DO NOTHING` so a re-run after a partial
   commit cannot raise.
4. `INSERT INTO opening_cache_repair_games (game_id, user_id, status) VALUES (…, 'pending')
   ON CONFLICT (game_id) DO UPDATE SET status = 'pending'`, and bump `rows_repaired`.
5. Set `opening_cache_audit.repaired_at = now()`.
