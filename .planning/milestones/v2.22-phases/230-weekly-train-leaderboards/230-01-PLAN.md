<objective>
Ship the weekly leaderboard backend foundation: one migration (users.leaderboard_hidden plus a partial solved_at index), server-side scoring constants pinned to the frontend by a parity test, a weekly aggregate query, a pure ranking service, and GET /api/train/leaderboard returning both boards (Points and Accuracy) for the viewer, including the private would-be rows for hidden and guest viewers and the Points pass target. The rank-without-this-session figure the score screen needs (D-12) is Plan 02, which extends this endpoint without changing its wire shape.

Purpose: every user-visible piece of Phase 230 (landing card, score-screen rank line, opt-out) reads this one endpoint. Proving "aggregate in SQL, rank in Python, visibility enforced server-side" end to end first catches any architectural dead end before the UI is built on it. The plan was split from an earlier 13-file backend plan so that a DB-heavy executor run stays short (project memory: executor subagents die mid-run on long DB-heavy plans).
Output: migration, User/DrillSolve model changes, app/services/train_score.py, app/repositories/train_leaderboard_repository.py, app/services/train_leaderboard.py, Leaderboard* schemas, the router endpoint, three test modules (router, service, parity).
