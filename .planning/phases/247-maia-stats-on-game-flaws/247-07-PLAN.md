<objective>
Run the full prod backfill, a catch-up re-run, and the prod coverage verification (D-12 steps 2-4), so every
mistake and blunder in fully evaluated prod games carries Maia stats.

EXECUTION MODE: ORCHESTRATOR-INLINE. Do NOT dispatch this plan to a gsd-executor subagent: the run takes about
16-21 hours, backgrounded children die with an agent, executor SSE sessions time out around 40 minutes, and subagents
cannot call the flawchess-prod-db MCP server (project memory). The orchestrator launches the run detached and polls it.

Purpose: D-12 makes the prod backfill part of the phase. Coverage of at least 99% with an explained NULL remainder
is the phase's completion bar.
Output: committed shard reports, `reports/maia-flaws-backfill/prod-coverage.md`, coverage numbers in the SUMMARY.
</objective>

  <action>
1. Launch detached (Bash caps foreground commands at 10 minutes, even with run_in_background): `mkdir -p temp/maia-flaws-backfill` then `setsid nohup bash -c 'PYTHONUNBUFFERED=1 uv run python -u scripts/backfill_maia_flaws.py --db prod --workers 9; echo EXIT=$?' >> temp/maia-flaws-backfill/prod-full.log 2>&1 < /dev/null & disown`. Record the parent python3 PID and the process group id (`pgrep -f` must match python3, not the uv wrapper).
2. Arm a persistent Monitor that every 15 minutes runs `uv run python scripts/backfill_maia_flaws.py --db prod --status` and `tail -n 3 temp/maia-flaws-backfill/prod-full.log`, prints a line only every 60 minutes and when the log gains an EXIT= marker or the recorded PID stops (`kill -0 <pid>`). Never test liveness with `pgrep -f "<pattern>"` inside the monitor: it matches the monitor's own command line. In zsh define shell functions instead of `$VAR` command strings (zsh does not word-split).
3. Expected pace: about 9 x 12 positions/s (dev smoke ms per position from 247-05-SUMMARY.md), so roughly 16-21 hours for ~7.6M flaws. Report progress to the owner from the Monitor lines; prod DB CPU can be watched through the MCP (`pg_stat_activity`, `pg_stat_user_tables.n_tup_upd` for game_flaws).
4. To stop early: `kill -TERM -- -<pgid>`; each shard finishes its batch, writes its report and exits 0. A tunnel drop makes shards exit with EXIT_SHARD_FAILED after 5 consecutive failed batches: restart the tunnel and relaunch the same command (the stamp is the checkpoint, nothing is redone).
5. On EXIT=0: append a "Full run" section to prod-coverage.md (run_stamp, wall time, combined total line, reason buckets) and commit all shard JSONs plus the file on main, then push.
