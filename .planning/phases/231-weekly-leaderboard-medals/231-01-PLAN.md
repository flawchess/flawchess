<objective>
Ship the medal snapshot end to end on the backend: the two new tables (standings + finalization marker) with the deletion-erasure trigger, the lazy idempotent finalizer that freezes each closed week's public boards into final standings with explicit medals, and the per-board `last_week` block (podium + the viewer's own non-medal final rank) on the existing `GET /api/train/leaderboard`.

Purpose: every visible medal surface (tally, podium, "You finished #N", claim dialog) reads this snapshot. Proving "finalize lazily on read, rank with the live board's own code, mask at read time" against a real request first catches any dead end before the claim API and UI are built on it. The board wire shape (`last_week`, and `medals` per row) is final after this plan, so the frontend board plan (03) can build against it in parallel with Plan 02.
Output: migration e3a8c5f17b20, the model module, the medals repository, `app/services/train_medals.py`, `final_standings` / `medal_for` / `build_last_week` in the leaderboard service, schema additions, the router finalizer call (with its failure-isolation test), two new test modules (router, service) and the extended leaderboard service and router tests. The repository-level finalization guarantees (idempotency, empty weeks, concurrent finalizers, trigger existence) and the runbook line are split into Plan 06 (wave 2) to keep this plan inside the context budget.
