## Planning notes

- **Shared function signature (discretion):** `server_graded_moves_for(*, source, ply, missed_pv_lines, best_move, ladder, herring_mover_color, key: PuzzleAnswerKey) -> list[ServerGradedMove]`. It takes the RAW key from `answer_key_for` (pre-legality) at both call sites, exactly as the solve path does today; legality and the "empty without a legal key" rule live in a separate composition-only step (`legal_server_graded_moves`). It must NOT return [] for a null key: the solve path still grades a played `su` server-side on a no-key soft puzzle today, and changing that would be a grading change.
- **Wire twin name:** `app.schemas.train.ServerGradedMove` (uci + tier only) mirrors the Phase 211 `VettedMove` same-name wire-twin precedent; the router imports only the wire one, the repository only the domain one.
- **Play == key is in the list** (soft best entry, herring ladder[0]); plan 05 excludes the key from the instant branch client-side (RESEARCH Open Question 1). Keeping it here keeps the wire list identical to `classification.graded_moves`.
- **Return shape:** `_answer_keys_by_position` returns `dict[int, PositionAnswerKey]` (key + composed set); the one existing direct caller in tests is updated.
