<objective>
Replace first-write-wins with two-source confirmation (CACHEFIX-08): provenance columns on
`opening_position_eval`, a candidate/promote/replace write path shared by the tick and the
submit lane, confirmed-only reads, and the D-11/D-12/D-13 refinements. Ships as Release 2,
after the prod repair, so `confirmed` means "two hash-asserted evaluations agree" rather
than "we hope so".

Purpose: the repair fixes the damage; this is what stops one bad write on a popular
position from tainting hundreds of games forever. A misaligned hash-to-eval pair would now
have to repeat identically, from a different game, to poison anything.

Output: the migration, the new write path, the confirmed-only read filter, and the
demote path.

<assumption_delta_decision>
**Noun now primary:** a cache row is no longer "the first engine eval anyone wrote for this
position". It is **a position eval confirmed by two independent hash-asserted sources**,
keyed by `full_hash`, written through ONE shared function regardless of which lane produced
it, and carrying its own provenance (`source_game_id`, `n_sources`, `engine_version`,
`written_at`, `confirmed_at`).

**Decision: promote.** `_upsert_opening_cache` becomes the only path into the cache, and the
tick's formerly-private write is demoted to one of its two callers (plan 02 made the submit
lane the second). Neither lane may reach the table any other way.

**Rationale (one line):** the phase's whole failure mode was that a single unverified write
from one lane became permanent truth for every later game, so the write must be a
confirmation protocol owned by one function, not an insert owned by whoever got there first.

**Suggested invariant test:** *every accepted engine result for an opening-region position,
from any lane, reaches `_upsert_opening_cache` exactly once with an asserted hash and a
truthful `source_game_id`.* The two concrete cases that would violate it are already covered:
D-13's self-promotion guard (`source_game_id` equal to the incoming game neither promotes nor
disagrees, test `self_promotion`) and the `_merge_dedup_pv_into_engine_map` self-confirmation
trap (the submit path snapshots `frozenset(engine_result_map)` before the merge, test
`submit_no_self_write` from plan 02).
</assumption_delta_decision>

## Decisions recorded by this plan

- **RESEARCH open question 2 resolved — the status-derived marking is BATCHED INSIDE the
  migration**, not moved to a `mark-confirmed` operator subcommand. Reason: Alembic runs on
  backend container startup (`deploy/entrypoint.sh`), and the `initial_fen` migration's
  docstring records the project's preference for "no manual production step and no window in
  which the column exists but is empty". An operator-run marking would leave a window in
  which every one of 2.57M rows is a candidate and opening dedup is effectively off. Lock
  and time implications, both of which the executor must measure on dev and record: the
  single seven-column `ALTER TABLE` takes one brief `ACCESS EXCLUSIVE` (constant defaults,
  so metadata-only, no table rewrite); the marking `UPDATE` is a real row rewrite over ~2.5M
  rows and runs as a keyset walk of 50k-row statements, each taking only `ROW EXCLUSIVE`.
  There is no batched-migration precedent in this repo, so the loop carries its own
  justification comment.
- **D-11 refines CACHEFIX-08's "within 50cp".** Agreement is
  `abs(expected_score(new) - expected_score(old)) <= OPENING_CACHE_AGREE_MAX_SCORE_DELTA`
  plus a mate/non-mate match. A fixed cp cut is wrong twice over: 100cp at +600 changes
  nothing while 55cp at equality is an inaccuracy boundary. The constant is a module constant
  in `eval_drain.py`, never a lookup into `opening_cache_repair_progress` — the app must not
  depend on that row existing at runtime (benchmark DB, dev, tests).
- **D-12 throttles the Sentry signal per row, not per event.** At a p99 floor roughly 1% of
  honest second sources look like disagreements, which over 2.6M positions would be ~26k
  events for nothing. Two consecutive misses on one position is the misalignment signature.
- **D-13 makes self-promotion impossible by construction** via `source_game_id BIGINT NULL`
  with **no FK**, deviating from CLAUDE.md's FK rule. Two reasons, both to go in the model
  docstring: the cache is a deliberately FK-free denormalized table (its `full_hash` PK
  references nothing either — "no FK, no cascade, no invalidation logic"), and a cache row
  must survive the deletion of the game that happened to source it, since the position eval
  is still valid. Reversibility: **one-way** (see the checkpoint in task 1).
- **`OPENING_CACHE_BACKFILL_SQL` is kept, not deleted** (CACHEFIX-08 offers both). Six tests
  execute it as the canonical gate. It gains `confirmed` in its INSERT column list with an
  explicit `false`: any backfilled row is a candidate, never confirmed.
- **The post-hardening re-audit mode is still NOT built** (CONTEXT deferred idea). The
  script docstring says so.
