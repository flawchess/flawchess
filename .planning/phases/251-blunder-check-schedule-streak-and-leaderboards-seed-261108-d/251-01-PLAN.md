<objective>
Lay the phase's schema and make the streak require both modes (D-02), end to end, before any UI or settings work.

Purpose: the streak machine is the load-bearing piece of Phase 251 and D-18 ships it to every streak holder at once with no
prod rehearsal. This plan keeps the pure tick machine byte-for-byte and changes only what feeds it: a set of complete days
computed from both session tables and the current per-mode sizes, plus one idempotent eager entry point that every
completion event calls.

Output: one Alembic migration with all non-leaderboard schema of the phase, the `day_is_complete` rule, the complete-day
feed into `tick_days`, blunder-check sessions that carry a session day and expire like puzzle sessions, and the launch-day
test matrix from CONTEXT Specifics.
</objective>

## Planning notes (recorded choices)

- Spec-less probe fallback: skipped. The phase has no requirement IDs to probe; decision coverage (D-01..D-25) is the
  contract instead.
- Assumption-delta scan: not detected (no checkpoint fired).
- Planner additions beyond RESEARCH (discretion area "streak day edge cases"), both reversible nullable columns:
  - `train_settings.streak_credited_on DATE`: the idempotency key of the eager path. RESEARCH proposed a
    `was_complete_before` guard computed with the current sizes; that misses the sequence "puzzles done with BC at 0 ->
    day credited -> BC raised -> BC done", which would mint a second freeze. A stored "last credited day" closes it.
    Backfilled to `streak_settled_through` so a user who completed today's puzzles before the deploy is not credited twice.
  - `train_settings.blunder_check_streak_from DATE`: the local launch day per existing row. Days before it are judged
    with blunder check not required, so pre-launch days stay as judged and the "N of M this week" caption does not drop
    for every streak holder on launch day. NULL on rows created after launch (rule always applies).
- Accepted assumption A8 (RESEARCH Pitfall 4, measured on prod 2026-11-18: 23 of 635 rows, 3.6%, have a sparse mask):
  blunder-check sessions are dated `local_today` like a fresh puzzle session; a sparse-mask user who splits the two modes
  across two days can lose that day. Accepted for launch, surfaced to the owner.
- Accepted assumption A6 (deviation from the orchestrator default, reason in RESEARCH Pitfall 3): puzzles are required
  whenever their size is above 0. `pool_state` is not "nothing to serve" (sharp fillers always compose a warm-up).
- Accepted assumption A9: never-started windows of an expired session are deleted so unseen blunders return to the pool.
