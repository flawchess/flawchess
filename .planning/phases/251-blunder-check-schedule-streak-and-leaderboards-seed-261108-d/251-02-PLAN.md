<objective>
Add the blunder-check Points and Score % weekly boards with medals, running through the existing ranking, finalization
and medal code (D-14, D-15 backend, D-22, D-23, D-25).

Purpose: blunder check pays about twice the points per item, so a merged board would shut out puzzle-only players (seed
reasoning behind D-14). Separate boards reuse one ranking implementation so finalization equals the live board.

Output: a BC weekly aggregate, a per-board spec instead of `if kind == ...` branches, four boards in the API, a migration
widening the stored board CHECK, and finalization/medal reads that know all four keys. The stored key names are a one-way
door, so a decision checkpoint sits before the task that first writes them.
</objective>

## Assumptions surfaced for the owner (not decisions to re-open)

- D-23 wording vs code (RESEARCH Open Question 1): CONTEXT says today's puzzle tally "already combines the two puzzle
  boards". The code folds tallies per board (`fold_medal_tallies`, `build_board` reads `tallies.get(kind)`, and the
  frontend copy says "that player's medals on this board"). This plan keeps per-board tallies on all four boards, which
  satisfies D-23's intent (a blunder-check row never shows puzzle medals). Combining the two puzzle boards would be a
  behaviour change to the puzzle boards and is NOT done here.
- A5: boards count every ended window regardless of session status; an abandoned window that never ended is excluded
  (a minor Score % exploit by abandoning after a timeout, accepted).
- RESEARCH Open Question 4: `rank_without_session` is null on blunder-check boards (the BC score screen links to the
  boards instead, D-24). Tie-breaks mirror the puzzle rule (value desc, count desc, name).
- Weeks finalized before deploy keep only the two puzzle boards (there were no public BC boards then).
</context>

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-251-05 | Information disclosure | BC boards (guests, hidden users) | high | mitigate | Reuse `_rank_board` / `resolve_viewer_visibility` unchanged; tests assert a guest or hidden user never appears on or shifts another viewer's BC board (D-25) |
| T-251-06 | Tampering | POST /train/medals/claim with BC board keys | medium | mitigate | Board validated by the widened Literal (422 otherwise); claim scoped to current_active_user; unknown keys match nothing |
