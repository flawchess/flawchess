<objective>
Make the offline re-tagger reproduce the live classify path exactly, and make its delta
report answer TAGFIX-09's question.

Purpose: three independent divergences mean the prod retag would NOT behave like a fresh
analysis, silently defeating the SC4 no-drift property the script's own docstring claims.
(1) `_worker_recompute` builds a sparse positions list that never fills `ply-1`, so plan
04's pre-flaw mate read and missed-orientation board build would see all-None in the retag
and a real row in the drain. (2) `fen_map` is a single synthetic entry, so plan 04's D-09
board build has no `fen_map[n-1]` to read and would silently fall back to the stackless
board in the retag only. (3) That single entry is `game_flaws.fen`, which is
piece-placement only — `chess.Board()` on it yields a board with NO castling rights and NO
en-passant target, so the retag cannot parse a castling flaw SAN and cannot replay an
en-passant capture. This is the exact bug class the Phase-148 D-02 fix removed from the
live path and it is still present here.

Separately, the delta report is written only under `--dry-run` and counts only
removed/survived, while TAGFIX-09 asks for removed/survived/shifted on the real writing
run — and D-11 shifts the depth of every surviving discovered-attack row without changing
its motif, which a motif-only shift counter would miss entirely.

Output: a retag whose 8-tuple provably equals the live classify result on a castling game
and an en-passant game, and a four-bucket report written on the run that actually writes.
</objective>
