<objective>
Make the drill answerable end to end on the server: a beta user starts window p, gets the lead-in and the first arrow,
answers each prompt "safe", "blunder" or "timeout", and the server grades it against the secret key, awards or
forfeits points, reveals the reply and the next arrow only after grading, hands out the better-move task on a caught
blunder, and finishes the session with points and Score %.

API shape (Claude's discretion, recorded): one call per answer. Batching is impossible under D-16 because each next
prompt depends on the previous grade, and sending the whole window would leak the punishing reply and the window length.

starting the next task. If a gsd-executor run dies mid-plan (project memory: SSE "Connection closed mid-response" on
long DB-heavy runs), re-dispatch with "resume at the first task without a commit" or let the orchestrator run the
remaining tasks inline; never redo a committed task. Read only the cited line ranges of 249-RESEARCH.md.

Purpose: plans 05 (better move, solution) and 06-07 (drill UI) build on this contract.
Output: pure grading module, drill service, three endpoints, tests.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> answers endpoint | the client asserts an answer and its own elapsed time; both untrusted |
| server payload -> client | anything sent before a window ends could reveal the key |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-249-10 | Information disclosure | start/answer payloads (D-16) | high | mitigate | incremental reveal: one arrow per prompt, reply only after its answer, no game id/ply/case/is_own/length pre-end; exact key-set and recursive forbidden-key tests |
