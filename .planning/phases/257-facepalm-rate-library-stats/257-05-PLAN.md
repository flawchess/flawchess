<objective>
Return three paired facepalm rows per time control from GET /library/flaw-comparison: the user's
facepalm blunders per 100 of their moves next to their opponents' in the same games, in total and
per type, with the gap, both rates, the counts and the significance, and no benchmark band.

Purpose: CONTEXT D-12 (unit and paired normalisation), D-13 (no band, significance computed but
colour-free), D-04 (types never compared with each other), D-06 (opponent scores aggregate-only),
D-01 / D-02 (the 0.7 cut and the type). Plan 06 renders these rows as the "Facepalm blunders"
card (D-11, D-14 to D-16).

Output: `fetch_facepalm_comparison` on a shared anchor, `FacepalmBullet` and
`FlawComparisonTc.facepalm_bullets` (both stacks), the fixture helpers plan 06 builds on, tests.

Split note (checker revision): this is the backend half of the former plan 04, kept on its own so
the DB-heavy query and its tests run in a short executor session; the card is plan 06.

Recorded assumptions (Claude's discretion, confirmed at UAT):
- Payload: the three rows join `FlawComparisonTc` (one cache entry, same gate and TC list) and are
  evaluated once per blunder in a fenced subquery (orchestrator decision 2). Research measured
  50 to 69 ms on dev user 28 on top of a 294 ms baseline. No split endpoint is pre-built; the prod
  `EXPLAIN` is a plan 07 manual item, and a separate endpoint is the fallback only if it is slow.
- Dev data: the opponent side is near zero on dev (144 of 5,624 opponent blunders scored for user
  28). The opponent-side visual read is a post-deploy prod check (plan 07); no dev backfill and no
  DB reset are planned.
</objective>
